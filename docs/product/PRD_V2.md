## Product Principle

본 프로토타입은 단순한 투자 챗봇이 아니라,
자연어 투자 의도를 실행 가능한 규칙으로 구조화하고
실제 시장 데이터로 검증한 뒤 사용자가 계획을 승인하는
의사결정형 트레이딩 프로덕트다.

기획·디자인·개발 전 과정에서
AI의 해석, 코드의 계산, 사용자의 최종 결정을 분리한다.
# AI Investment Plan Copilot

## Product Summary

아직 구체적이지 않은 투자 생각을
AI와의 짧은 대화로 실행 가능한 계획으로 정리하고,
실제 시장 데이터와 과거 가격에서 계획의 작동 방식을 검증한다.

AI는 시뮬레이션 결과를 바탕으로
자금 부담, 반복 매수 위험, 빠진 안전장치를 설명하고
사용자의 제약을 만족하는 복수의 조정안을 제시한다.

사용자는 기존 계획과 조정안을 비교해
최종 계획을 직접 선택하고,
실제 주문 없이 AI Agent의 작동 방식을 모의로 확인한다.

---

# 1. Problem

## 1.1 사용자는 완성된 투자 전략으로 시작하지 않는다

일반 개인 투자자는 다음처럼 막연한 생각에서 시작한다.

> 애플을 꾸준히 사고 싶다.

> 가격이 떨어질 때는 조금 더 사고 싶다.

> 한 달에 너무 많은 돈을 쓰고 싶지는 않다.

하지만 이를 실제 실행 계획으로 바꾸려면
다음 값을 직접 결정해야 한다.

- 종목
- 매수 주기
- 기본 매수 금액
- 추가 매수 기준
- 추가 매수 금액
- 월 최대 예산
- 추가 매수 횟수
- 계획 재검토 조건

현재의 투자 서비스는 사용자가 이미 이 값을 알고 있다고 전제하고
설정 화면이나 주문 폼부터 제공한다.

## 1.2 계획이 실제 시장에서 어떻게 작동하는지 알기 어렵다

투자 조건을 만들더라도 사용자는 다음을 판단하기 어렵다.

- 최근 시장에서 조건이 얼마나 자주 발생했는가
- 같은 달에 추가 매수가 몇 번 반복됐는가
- 계획대로라면 실제로 얼마의 자금이 필요했는가
- 하락이 이어졌을 때 추가 매수 위험이 얼마나 커지는가
- 언제 계획을 유지하고 언제 다시 검토해야 하는가

전문적인 백테스트 도구는 존재하지만,
일반 사용자가 직접 조건을 입력하고 결과를 해석하기 어렵다.

## 1.3 AI 결과를 그대로 믿기 어렵다

AI가 투자 전략이나 조정안을 제시하더라도
사용자는 다음 이유로 결과를 그대로 신뢰하지 않는다.

- 어떤 데이터가 사용됐는지 알기 어렵다.
- 숫자가 실제 계산인지 AI가 생성한 값인지 구분하기 어렵다.
- 하나의 정답처럼 제시돼 비교가 어렵다.
- AI가 계획의 위험보다 장점을 과도하게 강조할 수 있다.
- 최종 결정권이 사용자에게 있는지 불분명하다.

# 2. Target Customer

## Primary Target

투자할 종목에 대한 생각은 있지만,
구체적인 실행 조건과 위험 기준을 설계하기 어려운 개인 투자자

## Characteristics

- 종목은 직접 선택한다.
- 정기 매수나 하락 시 추가 매수에 관심이 있다.
- 전문적인 백테스트 경험은 부족하다.
- 장중에 시장을 계속 확인하기 어렵다.
- AI를 참고하지만 결과를 그대로 믿지는 않는다.
- 실제 주문 전에 계획의 작동 방식을 확인하고 싶다.
- 완전 자동화보다 사용자 승인과 모의 검증을 선호한다.

## Entry State

사용자는 다음 정도의 생각만 있어도 시작할 수 있다.

> 애플을 계속 모으고 싶은데,
> 가격이 떨어질 때 조금 더 사고 싶어.

완성된 매수 금액, 주기, 하락률을 미리 알고 있을 필요는 없다.

## Not Target

- AI에게 투자 종목 추천을 원하는 사용자
- 초단타 자동매매 사용자
- 전문 퀀트 전략을 직접 구현하려는 사용자
- 계좌 전체를 자동 운용하려는 사용자
- 미래 수익률 예측을 원하는 사용자

# 3. Job to Be Done

## Functional Job

투자 아이디어가 떠올랐을 때
복잡한 조건을 직접 설계하지 않고도
AI와 대화하면서 실행 가능한 계획으로 구체화하고 싶다.

계획을 실행하기 전
과거 시장에서 어떻게 작동했는지 확인하고
내 예산과 위험 허용 범위에 맞게 수정하고 싶다.

## Emotional Job

AI가 알아서 결정하는 것이 아니라
내가 이해하고 통제할 수 있는 계획이라고 느끼고 싶다.

## Social Job

전문 투자 도구를 배우지 않아도
근거를 확인하며 합리적으로 계획을 세우고 싶다.

# 4. Product Hypothesis

## Hypothesis 1. Guided Conversation

완성된 조건을 직접 입력하게 하는 것보다
AI가 필요한 질문을 한 번에 하나씩 제시하면
일반 사용자의 계획 작성 부담이 줄어들 것이다.

## Hypothesis 2. Live Structured Plan

대화와 함께 현재 계획이 구조화된 카드로 갱신되면
사용자는 AI가 자신의 의도를 어떻게 이해했는지
더 쉽게 확인하고 수정할 수 있을 것이다.

## Hypothesis 3. Historical Condition Replay (과거 조건 시뮬레이션)

이 제품의 분석은 **정식 백테스트가 아니다.** 최근 1년 가격에 현재 조건을 적용해
조건 발생 시점과 모의 실행 이벤트를 확인한다.

```text
사용자가 입력한 평균 매수가를 고정 기준으로 사용해
최근 가격에서 조건 발생 시점을 확인합니다.
실제 체결 수량, 환율, 평균 매수가 변화는 반영하지 않습니다.
```

MVP 가 구현하지 않는 것: 실제 주식 수량 · 환율 · 동적 평균 매수가 · 실제 체결 · 투자 수익률.

따라서 "이 전략을 1년 동안 실행했다면", "실제 투자 성과", "백테스트 수익률",
"실제 매수 결과", "수익성 검증" 같은 표현을 쓰지 않는다. 대신 "최근 1년 가격에 현재 조건을
적용하면", "조건 발생 시점", "모의 실행 이벤트" 로 쓴다.

수익률 대신 다음 정보를 보여주면
사용자가 계획의 작동 방식을 이해하기 쉬울 것이다.

- 조건 발생 횟수
- 월별 투자 금액
- 반복 추가 매수 횟수
- 예산 초과 기간
- 조건 발생 후 추가 하락폭

## Hypothesis 4. Multiple Alternatives

AI가 하나의 최적안을 추천하는 것보다
서로 다른 장단점을 가진 복수의 조정안을 제시하면
사용자의 결정권과 신뢰가 높아질 것이다.

## Hypothesis 5. Explainable AI

AI 설명이 실제 시장 데이터와
재현 가능한 코드 계산 결과에 연결되면
사용자는 AI 결과를 더 신뢰할 수 있을 것이다.

# 5. Product Principles

## 5.1 AI는 투자 결정을 대신하지 않는다

AI는 다음 역할만 수행한다.

- 사용자의 생각을 이해한다.
- 빠진 조건을 질문한다.
- 계획을 구조화한다.
- 계산 결과를 설명한다.
- 조정 가능한 대안을 제시한다.

최종 계획과 실행 여부는 사용자가 결정한다.

## 5.2 계산은 코드가 담당한다

다음 값은 AI가 생성하지 않는다.

- 조건 발생 횟수
- 월별 투자 금액
- 조건 기준가 (사용자가 입력한 고정 평균 매수가에서 계산)
- 추가 매수 횟수
- 예산 초과 여부
- 조건 발생 후 추가 하락폭
- 조정안 적용 결과

모든 수치는 TypeScript 시뮬레이션 엔진에서 계산한다.

## 5.3 대화와 구조화된 UI를 구분한다

### 대화를 사용하는 경우

- 사용자의 투자 의도 파악
- 누락 정보 확인
- 결과에 대한 추가 질문
- 계획 수정 요청
- 조정안 설명

### 구조화된 UI를 사용하는 경우

- 현재 계획
- 시장 데이터
- 차트
- 시뮬레이션 결과
- 위험 항목
- 변경 전후 비교
- 최종 승인

## 5.4 중요한 정보는 숨기지 않는다

반드시 화면에 표시한다.

- 데이터 출처
- 데이터 기준 시각
- 지연 시세 여부
- 시뮬레이션 기간
- AI 설명에 사용된 계산 결과
- 실제 주문이 아니라는 사실

# 6. Core Experience

## Stage 0. Onboarding

사용자에게 제품이 무엇을 도와주는지 먼저 설명한다.

### Message

투자 계획을 같이 점검해볼까요?

정확한 조건을 아직 몰라도 괜찮아요.

1. 계획을 함께 구체화해요.
2. 실제 데이터에서 작동 방식을 확인해요.
3. 감당 가능한 범위로 조정해요.

### Actions

- 내 계획 이야기하기
- 예시 계획으로 둘러보기

### Safety Message

종목을 추천하거나 실제 주문을 실행하지 않아요.

---

## Stage 1. Discover

사용자가 막연한 투자 생각을 말한다.

### Example

> 애플을 꾸준히 사고 싶은데,
> 가격이 떨어질 때 조금 더 사고 싶어.

AI는 입력에서 확인 가능한 내용을 먼저 구조화한다.

### Extracted

- 종목: 애플
- 기본 행동: 정기 매수
- 추가 행동: 하락 시 추가 매수

AI는 이미 확인한 내용을 다시 묻지 않는다.

---

## Stage 2. Clarify

AI가 계획 실행에 필요한 조건을
한 번에 하나씩 질문한다.

### Question Priority

1. 종목
2. 기본 매수 주기
3. 기본 매수 금액
4. 추가 매수 기준
5. 하락률
6. 추가 매수 금액
7. 월 최대 예산

### Interaction

각 질문에는 다음을 함께 제공한다.

- 질문
- 질문이 필요한 이유
- 빠른 선택
- 직접 입력
- 이전 단계 수정

### Example

정기적으로 얼마씩 사고 싶은가요?

매주 투자할 수 있는 금액을 알려주면
월별 자금 부담을 함께 계산할 수 있어요.

- 매주 30,000원
- 매주 50,000원
- 직접 입력

---

## Stage 3. Live Plan Card

대화 화면에는 항상
현재까지 정리된 계획을 함께 보여준다.

### Example

현재까지 정리한 계획

Apple Inc. · AAPL

정기 매수
매주 50,000원

추가 매수
평균 매수가보다 3% 하락 시 20,000원

월 최대 예산
200,000원

### Requirements

- AI 답변마다 즉시 갱신한다.
- 미확정 값은 `확인 필요`로 표시한다.
- 사용자가 카드에서 값을 직접 수정할 수 있다.
- 수정 시 대화 상태와 Strategy 객체도 함께 갱신한다.

---

## Stage 4. Agent Execution Approval

필수 정보가 채워지면
AI가 실행할 작업을 먼저 설명한다.

### Message

계획을 검토할 준비가 됐어요.

다음 내용을 확인할게요.

- 애플의 현재 시장 가격
- 최근 1년 동안 조건이 발생한 시점
- 월별로 필요했던 투자 금액
- 하락이 이어졌을 때의 추가 위험
- 빠진 금액·횟수 제한

약 10초 정도 걸릴 수 있어요.

### CTA

실제 데이터로 검토하기

사용자 승인 없이 시장 데이터 조회와
시뮬레이션을 시작하지 않는다.

---

## Stage 5. Agent Tool Activity

AI 내부 사고과정이 아니라
실제 도구 실행 상태를 보여준다.

### Steps

- 애플 AAPL을 확인했어요.
- 현재 시장 가격을 불러왔어요.
- 최근 1년 거래일 데이터를 확인했어요.
- 입력한 조건을 과거 가격에서 실행하고 있어요.
- 위험과 조정 방법을 정리하고 있어요.

### Data Source

- Claude
- Market API
- TypeScript Simulation Engine

### Requirements

- 실제 작업 완료 상태와 화면 상태가 일치해야 한다.
- 가짜 퍼센트 진행률을 사용하지 않는다.
- 실패한 단계에서 오류 원인과 재시도 기능을 제공한다.
- API 실패 시 fixture로 자동 대체하지 않는다.

---

## Stage 6. Simulation Workspace

분석 결과는 채팅 말풍선이 아니라
데이터 중심 워크스페이스로 보여준다.

### 6.1 AI Summary

예시:

> 현재 계획대로라면
> 일부 기간에서 월 예산을 넘을 수 있어요.

최근 1년 가격에서 하락 조건이
한 달에 최대 [실제 계산 후 반영]번 발생했어요.

> **example placeholder** — 문장 구조 예시이며, 숫자는 시뮬레이션 엔진 계산값으로 채운다.

### 6.2 Market Data

- 회사명
- 티커
- 현재가 또는 직전 종가
- 전일 대비
- 기준 시각
- 지연 여부
- 출처

### 6.3 Historical Chart

최근 1년 가격 차트에 다음 이벤트를 표시한다.

- 정기 매수
- 추가 매수 조건 발생
- 월 예산 초과
- 재검토 조건 발생

### 6.4 Simulation Metrics

- 정기 매수 횟수
- 추가 매수 조건 발생 횟수
- 총 추가 투자 금액
- 한 달 최대 추가 매수 횟수
- 월 최대 투자 금액
- 월 예산 초과 개월
- 조건 발생 후 최대 추가 하락폭

### 6.5 Risk Review

AI는 계산된 값과 연결된 위험만 설명한다.

# 7. Functional Requirements

## FR-01. 시작 안내

- 제품 역할과 3단계 과정을 설명한다.
- 완성된 투자 조건이 없어도 시작할 수 있음을 알린다.
- 투자 추천과 실제 주문을 제공하지 않음을 표시한다.

## FR-02. 자연어 입력

- 사용자가 자유 문장으로 투자 생각을 입력할 수 있다.
- 한국어 종목명과 영문 티커를 지원한다.
- 입력 내용을 원문으로 보존한다.

## FR-03. 대화 상태 관리

- 현재 질문과 답변 이력을 유지한다.
- 이미 확인한 정보를 다시 묻지 않는다.
- 사용자가 이전 답변을 수정할 수 있다.
- 수정 시 이후 계산 결과를 무효화하고 다시 계산한다.

## FR-04. 계획 구조화

AI는 다음 필드를 구조화한다.

- 종목
- 시장
- 기본 매수 행동
- 기본 매수 주기
- 기본 매수 금액
- 추가 매수 기준
- 하락률
- 추가 매수 금액
- 월 최대 예산
- 추가 매수 최대 횟수
- 재검토 조건

## FR-05. 누락 조건 탐지

- 필수 정보가 없으면 질문을 생성한다.
- 숫자를 임의로 채우지 않는다.
- 질문이 필요한 이유를 함께 설명한다.

## FR-06. 실시간 계획 카드

- 대화 결과를 구조화된 카드로 표시한다.
- 미확정 값은 `확인 필요`로 표시한다.
- 카드에서 직접 편집할 수 있다.

## FR-07. 시장 데이터

- 종목 검색
- 현재가 또는 직전 종가
- 전일 대비
- 기준 시각
- 최근 1년 일별 가격

시장 데이터가 실패하면
분석을 중단하고 오류를 보여준다.

## FR-08. 시뮬레이션 엔진

다음 항목을 TypeScript에서 계산한다.

- 정기 매수 모의 실행 이벤트
- 추가 매수 조건 발생
- 월별 총 투자 금액
- 월별 추가 매수 횟수
- 예산 초과 여부
- 조건 발생 후 추가 하락폭
- 재검토 조건 발생

평균 매수가는 **사용자 입력값을 고정 기준으로 사용하며 갱신하지 않는다.** MVP 는 KRW 금액을
USD 주식 수량으로 환산하지 않아 가중평균 매수가를 계산할 수 없다. 임의의 환율·수량을 가정해
근거 없는 숫자를 만들지 않는다.

## FR-09. 차트

- 최근 1년 가격을 표시한다.
- 정기 매수와 추가 매수 이벤트를 구분한다.
- 예산 초과와 재검토 이벤트를 표시한다.
- 이벤트를 선택하면 날짜와 이유를 보여준다.

## FR-10. AI 위험 설명

- 계산 결과에 근거한 내용만 설명한다.
- 위험을 단정하거나 공포스럽게 과장하지 않는다.
- 계획의 장점과 반대 근거를 함께 보여준다.

## FR-11. 자연어 수정 요청

- 사용자가 변경하고 싶은 제약을 문장으로 입력할 수 있다.
- AI가 제약을 구조화한다.
- 모호한 요청은 다시 질문한다.

## FR-12. 조정안 생성

- 최소 2개의 대안을 제공한다.
- 각 대안은 서로 다른 우선순위를 가져야 한다.
- 각 대안은 사용자의 제약을 충족해야 한다.
- 각 대안은 시뮬레이션 엔진으로 다시 계산한다.

## FR-13. 비교

- 기존 계획과 조정안을 동일 지표로 비교한다.
- 바뀐 값과 유지된 값을 구분한다.
- 사용자가 조정안을 선택하거나 다시 수정할 수 있다.

## FR-14. 최종 승인

- 사용자가 선택한 계획을 다시 요약한다.
- 실제 주문이 아님을 확인한다.
- 사용자의 명시적 승인 이후에만 모의 실행한다.

## FR-15. 과거 Agent 재생

- 과거 데이터의 주요 이벤트를 시간순으로 보여준다.
- 각 이벤트에서 Agent가 어떤 결정을 내렸는지 설명한다.
- 제한 조건 때문에 실행되지 않은 이벤트도 표시한다.

## Scenario 1. 불완전한 정기 매수 계획

기대 결과:

- 추가 매수는 임의로 제안하지 않는다.
- 계획 카드에는 미확정 값을 표시한다.

## Scenario 2. 하락 시 추가 매수

입력:

> 애플을 매주 5만 원씩 사고,
> 평균 매수가보다 3% 떨어지면 2만 원 더 사고 싶어.

기대 결과:

- 종목, 주기, 금액, 하락률을 구조화한다.
- 평균 매수가를 질문한다.
- 월 예산과 횟수 제한이 없음을 위험으로 탐지한다.

## Scenario 3. 모호한 계획

입력:

> 테슬라를 천천히 모으다가 많이 오르면 좀 팔고 싶어.

기대 결과:

- `천천히`, `많이`, `좀`에 해당하는 값을 임의 생성하지 않는다.
- 주기, 금액, 상승률, 매도 비율을 질문한다.

## Scenario 4. 예산 제약

입력:

> 정기 매수는 유지하면서
> 한 달에 20만 원을 넘지 않게 해줘.

기대 결과:

- 월 최대 예산 200,000원을 제약으로 구조화한다.
- 서로 다른 조정안 2개를 생성한다.
- 두 조정안 모두 월 예산을 넘지 않는다.

## Scenario 5. API 실패

기대 결과:

- 임의 가격이나 fixture를 보여주지 않는다.
- 실패한 데이터와 재시도 행동을 표시한다.

# 12. Safety and Trust

- AI가 투자 종목을 추천하지 않는다.
- 수익률을 예측하거나 보장하지 않는다.
- 사용자가 입력하지 않은 숫자를 임의 생성하지 않는다.
- 모든 수치는 코드 계산 결과를 사용한다.
- 시장 데이터 출처와 기준 시각을 표시한다.
- 과거 시뮬레이션이 미래 성과를 의미하지 않음을 표시한다.
- 실제 주문이 실행되지 않음을 반복해서 안내한다.
- 조정안을 자동 적용하지 않는다.
- 사용자가 비교하고 직접 선택한다.
- API 오류를 숨기지 않는다.
- AI 설명과 계산 결과를 구분한다.

# 13. Prototype Completion Criteria

다음 전체 루프가 실제로 작동해야 한다.

```text
시작 안내
→ 막연한 투자 생각 입력
→ AI 추가 질문
→ 계획 카드 갱신
→ 사용자 실행 승인
→ 실제 시장 데이터 조회
→ 과거 시뮬레이션
→ AI 위험 설명
→ 자연어 수정 요청
→ 조정안 2개 계산
→ 변경 전후 비교
→ 사용자 최종 선택
→ 과거 Agent 재생
```
완료 조건:

- Claude 응답이 실제 계획 카드에 반영된다.
- AI가 누락된 숫자를 임의 생성하지 않는다.
- 실제 시장 API 데이터가 표시된다.
- 최근 1년 가격 데이터를 사용한다.
- TypeScript가 시뮬레이션 값을 계산한다.
- 조정안마다 시뮬레이션 결과가 달라진다.
- 사용자 제약을 만족하지 않는 조정안은 노출하지 않는다.
- 최종 선택 전후 계획이 명확히 구분된다.
- 실제 주문은 실행하지 않는다.
- 실패 상태를 사용자가 확인할 수 있다.

# 14. Open Questions

인터뷰와 기술 스파이크 이후 확정한다.

- 사용자는 막연한 생각에서 시작하는가, 완성된 조건에서 시작하는가
- 첫 질문은 종목, 목표, 투자 금액 중 무엇이 자연스러운가

- 현재 계획 카드는 채팅 화면 상단과 하단 중 어디가 적합한가
- 과거 시뮬레이션에서 가장 먼저 보는 지표는 무엇인가
- 사용자는 복수 대안을 실제로 비교하고 싶어 하는가
- 조정안의 장단점을 어느 수준까지 설명해야 하는가
- 과거 Agent 재생이 실제 자동화 이해에 도움이 되는가
